# EduNova — Prioritized Task List

Derived from [PRD.md](./PRD.md). Ordered by dependency and impact, not by repo — do them roughly top to bottom. Each task tags which repo(s) it touches: 🟦 Flutter (`edunova`) · 🟩 Go (`edunova-server`) · 🟨 Next.js (`edunova-admin`).

## P0 — Prerequisites (block everything class-scoped or progress-related)

1. ✅ 🟩 **Backfill + validate `student_class`.** Added `binding:"oneof=3 4 5 6 7 8"` to registration/profile-update requests, plus a `runStudentClassCleanupMigration()` that extracts digits from values like `"Class 4"` and clears anything else unmappable (`"one"`, `""`) rather than guessing. Verified live: all rows now hold `"3"`–`"8"` or `""`, no more garbage values.
2. ✅ 🟨🟦 **Fix notes subject-taxonomy mismatch.** Admin's `SUBJECTS` constant now stores English `value`s (matching Flutter's filter chips exactly) with Bengali `label`s for display — same `{value, label}` pattern `daily-content` already used. Added the two subjects Flutter was missing (Social Science, Biology) to its filter chips so the full taxonomy is reachable.

## P1 — Auth & Onboarding (foundational, unblocks the guided-profile experience)

3. ✅ 🟦🟩 **Remove Google/Gmail login.** Deleted `POST /api/auth/google`, the `GoogleAuth` handler, `verifyGoogleToken`, and `GoogleAuthRequest` (Go); deleted the dead `loginWithToken` stub (Flutter, had zero callers). Mobile+password is now the only path.
4. ✅ 🟦🟩 **Add class + confirm-password to registration.** Go `RegisterRequest` now requires `student_class` (validated 3–8) and registration inserts it directly. Flutter register screen gained a class-chip picker and a confirm-password field (reusing existing `confirmPassword`/`passwordsDontMatch` l10n strings).
5. ✅ 🟦 **Expand profile-setup into a guided wizard.** Added Family (father/mother name + mobile) and Address sections to `profile_setup_screen.dart`, reusing fields that already existed on the backend `User` model. Class is now pre-filled from registration instead of asked again. `isProfileComplete` extended to require address + father contact, so the app correctly routes guardians through the fuller setup before reaching home.

## P2 — Progress & Results (the core value proposition — biggest single build)

6. ✅ 🟨 **Build offline exam score entry UI.** New `/admin/results` page: student search (reusing the existing `AdminSearchUsers` endpoint), subject/exam/date/marks form, editable table. Added to the admin sidebar nav.
7. ✅ 🟩 **Design + build results/progress data model & endpoints.** New `student_results` table (migration guarded, runs once) + `handlers/results.go`: admin CRUD (`/admin/results`) and student-facing `GET /results` (raw list) + `GET /results/summary` (overall %, per-subject averages, weakest-subjects-first improvement areas capped at 3, recent 10). Caught and fixed a real bug during testing: `exam_date` is a Postgres `DATE` column that pgx scans as `time.Time`, but I'd scanned it into a Go `string` — every row silently failed to scan (swallowed by a bare `continue`), so the list endpoint always returned `[]` despite rows existing. Fixed by casting `exam_date::text` in the SELECT queries. Verified end-to-end with real data after the fix (overall%, per-subject breakdown, and improvement-area flagging all confirmed correct).
8. — *(folded into #6 — one page handles both authoring and browsing; a separate "authoring screen" wasn't needed once the CRUD table was built)*
9. ✅ 🟦 **Build the guardian-facing results/progress view.** New `lib/features/results/`: service + `/results` screen (overall % card, per-subject breakdown with progress bars, improvement-areas callout, recent exam list) reachable from a real progress-summary card on the home tab (was empty space before) and a quick-access icon. Also replaced the `profile_tab.dart` stat row's hardcoded mock values (`'12'`, `'48'`, `'89%'`) with real data from `/user/dashboard` and `/results/summary`.

## P3 — Routine & Attendance (guardian visibility into the offline batch)

10. ✅ 🟨🟩 **Structure `Batch.schedule` into real day/time fields.** Added `days text[]`, `start_time`, `end_time` columns (migration ALTERs, guarded/idempotent). `schedule` is now a derived, human-readable string generated server-side (`buildScheduleText` + 12h `formatTime` in `handlers/batch.go`) so every existing display that reads the plain `schedule` field kept working unchanged. Next.js batch form replaced the free-text input with day-toggle chips + native time pickers. Verified: old free-text batches (`schedule: "Mon"`) untouched; a new structured batch correctly generated `"Sat-Mon-Wed, 5:00 PM - 7:00 PM"`.
11. ✅ 🟩🟦 **Expose batch schedule to the student side.** Added `COALESCE(b.schedule,'')` to the `GetUserEnrollments` join (was previously not selected at all) and a matching `batchSchedule` field on Flutter's `Enrollment` model, now shown on `my_enrollments_screen.dart`. A dedicated home-dashboard "routine" widget is still open — that's part of the bigger P4 home rebuild.
12. ✅ 🟩 **Add student-facing attendance-history endpoint.** New `GET /api/attendance/my` — the logged-in account's own attendance records plus a computed present/absent/late breakdown and attendance rate. Verified end-to-end (1 present + 1 absent → 50% rate, correct).
13. ✅ 🟩 **Fixed the broken parent-notification lookup and extended notification coverage.** The old code tried to resolve a *separate* "parent account" by phone number — but per our settled architecture (single shared login, no separate guardian account), that premise doesn't hold, so I simplified `sendAttendanceNotification` to push directly to the logged-in account's own device tokens instead of the broken lookup. Notifications now fire for every status (present/absent/late), not just "present" — a guardian arguably cares more about an absence than a presence. Also found and fixed the **same `DATE`-scanned-as-`string` bug** (see task 6/7 note) in `AdminGetAttendance` and `AdminGetHolidays`/`AdminCreateHoliday` — both silently returned empty results the same way the results endpoint did; confirmed live before and after the fix.

## P4 — Guardian-First Home Dashboard (ties P2 + P3 together)

14. ✅ 🟦 **Rebuild the Flutter home tab** into an organized dashboard: added a routine card (active batch + schedule, from the enrollments endpoint extended in P3) and a notifications preview (unread badge + latest title) above quick access, and free courses now filter by the student's own class automatically instead of showing everything. Results/progress summary card was already added in P2. A dedicated notes preview was skipped — the quick-access "নোটস" icon already one-taps there, and a content preview didn't clear the value bar for the added complexity.
15. ✅ 🟨🟩 **Surface guardian fields on the Users admin list.** Found the root cause was one level deeper than expected: `AdminGetUsers` (Go) never selected `father_name`/`father_mobile`/`mother_name`/`mother_mobile`/`student_class` from the database at all — the Next.js `User` type *claimed* those fields existed, but the API silently omitted them, so they were `undefined` at runtime despite TypeScript insisting otherwise. Fixed the Go query (both the search and non-search branches) and added Class + Guardian columns to the admin table. Verified live: an account with `student_class: "4"` now actually returns it.
16. ✅ 🟦 **Simplify course browsing.** Class now defaults to the student's own (from cached profile, no extra tap needed for most guardians). Replaced the two cramped inline dropdowns with two horizontally-scrollable chip rows (type, then class) stacked below the search bar, matching the touch-friendly chip pattern already established in `notes_screen.dart`/`daily_content_screen.dart` elsewhere in the app, instead of introducing a third UI convention.

## P5 — Phase 2: Interactive Practice (after MVP ships)

17. ✅ 🟨🟩 **Designed and built the flashcard/vocabulary + sentence-construction data model.** Three new tables: `vocabulary_words` (word/meaning/meaning_bn/example, class-tiered 3–8 — doubles as both flashcard content and the source pool for auto-generated MCQ quiz questions), `sentence_exercises` (a prompt word + a sample answer for self-checking, since free-text sentences aren't machine-gradable), and `practice_attempts` (one row per flashcard review / quiz answer / sentence submission — nothing is pre-aggregated, so points/streak logic can change without a backfill). Admin CRUD at `/admin/vocabulary` and `/admin/sentence-exercises`. Seeded 30 vocabulary words (5/class) and 12 sentence exercises so the feature works out of the box — caught during testing that my first seed pass only had 3 words/class, one short of the 4 needed to generate a 4-option quiz, so the quiz silently returned nothing for every class; fixed by expanding the seed set and verified live.
18. ✅ 🟦 **Built the practice-session UI.** New `lib/features/practice/`: a hub screen (level/points/streak card + 3 activity tiles), a flip-to-reveal flashcard screen, a 4-option MCQ vocabulary quiz with a score summary, and a sentence-builder screen (type a sentence, reveal the sample answer to self-check). Reachable from the home quick-access row — swapped out "ট্রানজিশন" (a niche, already-otherwise-reachable feature) for "অনুশীলন" (Practice) there, since practice is far more central to the new vision.
19. ✅ 🟩 **Added attempt tracking, a real consecutive-day streak, and a point/level model.** `GET /api/practice/stats` computes everything live from `practice_attempts`: total points (10/correct quiz answer, 2/wrong, 3/flashcard reviewed, 5/sentence attempted), level (`points/100 + 1`), and — unlike `daily_content`'s streak, which is actually a lifetime distinct-item count — a real streak computed by walking backward day-by-day from today until a gap is found. Verified live: a fresh account doing one of each activity today showed `current_streak: 1` correctly. This is intentionally a separate system from the P2 results dashboard for now (practice points aren't academic results), not merged into `overall_percent`.
